# product-spec 스킬 v4 설계

## 용어

| 용어 | 뜻 |
|---|---|
| 스펙 | 개발 킥오프용 실행 문서. 이 스킬이 만드는 산출물 |
| 코드 식별자 | 용어에 대응하는 이벤트명, API 경로, 필드명, 컴포넌트명. 출처에서 그대로 복사한 것만 인정 |
| 골격 초안 | 스펙의 구조와 출처 있는 내용만 채운 첫 출력. 빈칸에는 질문 번호가 붙음 |
| 도메인 팩 | 대상 서비스의 메뉴 구조, 기존 스펙, 용어, API 등 사실 정보를 모은 파일. `docs/spec-context.md` |
| 출처 | AI가 문장을 쓸 수 있는 근거. 코드, 첨부 자료, 대화에서 작성자가 말한 것, MCP로 읽은 기존 문서 네 가지만 인정 |
| 리뷰 체크리스트 | req-review 스킬의 6개 대항목(사용자와 권한, 정책, 사용자 시나리오, 기능 상세 명세, UI 명세, 데이터 연동 명세) |
| 다이어그램 블록 | Confluence에 설치된 Mermaid Chart 앱의 매크로. 코드와 렌더된 PNG를 함께 담음 |
| 첨부 이미지 | Confluence 페이지 첨부 파일로 올린 PNG를 본문에 이미지로 넣는 방식 |
| 작성자 토큰 | 스킬을 실행하는 사람 본인의 Atlassian API 토큰. 환경변수로 주입 |

## 배경과 목표

- 현재 스킬(v3.2)은 호출 즉시 모든 섹션을 추론으로 채워 출력함. 도메인 지식(메뉴 구조, 히스토리) 없이 쓴 문장이 많아 작성자가 읽고 고치는 시간이 새로 쓰는 시간보다 김
- 섹션이 12개라 작업자가 실제로 보는 구현 표가 앞뒤 서사에 묻힘
- 다이어그램은 코드만 넣고 사람이 직접 Confluence에 붙여넣게 돼 있음
- 목표: 출처 있는 내용만 쓰고, 빈칸은 리뷰 체크리스트를 거쳐 질문으로 받아 채우며, 다이어그램은 그림으로 자동 삽입되는 스킬로 재구성

## 결정 사항 (2026-09-17 합의)

1. 포크(suziejang-po/product-spec-skill)에서 작업. 원본 레포 PR은 이후 판단

7. 구현 상세 표는 번호, 진입점, 화면, 기능, 요구사항이 각각 열. 기능 하나가 한 행 (2026-09-17 교정)

9. 코드 식별자는 출처에서 복사한 것만. 없으면 빈칸 (2026-09-17 교정)
10. 현재 수치마다 근거 링크. Confluence 게시 시 수치 셀에 인라인 댓글로 쿼리 첨부 (2026-09-17 교정)
11. 본문 완성 뒤 아티팩트 시각화(HTML 프로토타입, 흐름 시각화) 제작 여부를 한 번 물음. 기본값은 만들지 않음 (2026-09-17 교정)

## 실행 흐름

### Phase 0. 컨텍스트 수집

- 레포 스캔은 유지하되 git log로 서사를 만들지 않음. 커밋 메시지는 변경 범위 파악에만 씀
- `docs/spec-context.md`(도메인 팩)가 있으면 읽음. 없으면 아래 항목을 작성자에게 한 번에 물어 만들고 저장함
  - 대상 서비스와 화면 (URL 또는 화면명)
  - 관련 기존 스펙과 히스토리 링크 (Confluence 검색으로 후보를 먼저 제시)
  - 메뉴 구조 (depth1, depth2)
  - 용어와 코드 식별자 (API 필드, 이벤트명, 컴포넌트명)
  - 관련 API 스펙 (asp MCP가 있으면 자동 조회)
  - 이벤트명 존재 여부 (Amplitude MCP가 있으면 택소노미 검색으로 확인. 있으면 '기존', 없으면 '신규 제안'으로 표기)
- 도메인 팩은 같은 프로젝트의 다음 스펙에서 재사용함. 갱신은 작성자가 요청할 때만

### Phase 1. 골격 초안 출력

- 출력 범위: 용어 표, 메타, 문제, 사용자 니즈, 가설과 KR, 대안, 구현 범위 요약(변경 페이지 표, 메뉴 구조 표, 플로우 다이어그램). 구현 상세 표는 페이지 이름과 행 제목만 잡고 설명 칸은 비움
- 출처 규칙: 도메인 서술은 출처가 있을 때만 씀. 출처가 없는 칸은 문장을 만들지 않고 비워 두고 `[Q3]` 형식의 질문 번호만 붙임
- 초안 끝에 출처 요약을 한 줄씩 붙임 (예: "메뉴 구조: spec-context.md", "KR 목표값: 없음, Q5")
- 용어 표의 코드 식별자는 출처에서 그대로 복사. 유추한 이름을 쓰지 않음. 확인하지 못하면 빈칸
- 현재 수치는 근거(Amplitude 차트 링크, BQ 쿼리)와 함께 적음. 근거가 없으면 수치 옆에 ⚠️ 쿼리 첨부 필요
- 문서 유형(New Product, Feature, Enhancement) 판별은 유지. 유형에 따라 섹션 축약

### Phase 2. 내부 리뷰

- `references/review-checklist.md`의 6개 대항목으로 초안을 판정 (정의됨, 불충분, 정의 없음)
- 문서 유형이 Enhancement면 사용자와 권한, 정책 항목은 변경과 관련 있을 때만 봄
- 판정 결과를 사용자에게 표로 출력하지 않음. 질문 변환의 입력으로만 씀

### Phase 3. 질문

- 초안의 빈칸과 리뷰의 미정의, 불충분 항목을 합쳐 질문으로 바꿈
- `references/question-map.md`의 매핑표에 따라 질문마다 답이 들어갈 섹션과 셀이 정해짐
- 대항목별로 묶어 한 번에 5개 안팎. 선택지가 있는 질문은 선택지형으로(AskUserQuestion 가능 환경이면 그것을 씀)
- 최대 2회. 2회 후에도 답이 없는 항목은 본문에 ⚠️와 확인 주체를 인라인으로 남김 (예: "⚠️ 개발 확인 필요", "→ 논의 필요"). 문서에 '미결'이라는 라벨은 쓰지 않음
- 작성자가 "모른다", "나중에"라고 답한 항목도 ⚠️로 남기고 지어내지 않음

### Phase 4. 본문 완성과 자가 검증

- 답변을 매핑된 셀에 채워 전체 본문 출력
- 자가 검증 항목
  - 출처 없는 도메인 서술이 남아 있지 않은가
  - 페이지당 표 1개, 셀당 3줄 이내, 문단 서술 없음
  - 금지 패턴 없음: 결정 이력 서술("정정", "재검증", "철회"), 같은 수치의 반복, "맥락:" 라벨, 가운데점, 원형 숫자, 줄표
  - 용어 표의 용어만 본문에 쓰였는가 (동의어 사용 없음)
  - 다이어그램이 코드가 아니라 그림으로 들어갔는가
- 저장: `docs/PRODUCT_SPEC.md`, `docs/diagrams/*.mmd`(코드), `docs/diagrams/*.png`(그림)
- 저장 뒤 질문 하나: 아티팩트 시각화를 만들지. 선택지는 화면 프로토타입 HTML(기존 Prototype 규칙), 흐름 인터랙티브 시각화 HTML, 만들지 않음. 기본값은 만들지 않음. 만들면 구현 범위 요약의 비주얼 표에 경로를 적음

### Phase 5. Confluence 게시

- 기존 스킬의 게시, 갱신, 충돌 검사, 이동 절차는 유지
- 다이어그램 삽입은 아래 「다이어그램 파이프라인」을 따름
- 결정 이력은 본문에 쓰지 않고 Confluence 버전 코멘트로만 남김
- 수치 셀마다 인라인 댓글로 근거 쿼리 또는 차트 링크를 첨부 (`createConfluenceInlineComment`). 근거가 없는 수치는 댓글 대신 본문의 ⚠️만 남김
- 표 HTML의 번호 열은 `data-colwidth`로 좁게 고정하고 `data-display-mode="fixed"`를 씀

### 수정 모드

- 기존 스킬의 수정 모드(변경 섹션만 출력, 백업, 머지)는 유지
- 다이어그램에 영향이 있는 수정이면 `.mmd`를 고치고 재렌더해 다시 삽입

| 순서 | 섹션 | 내용 |
|---|---|---|

| 6 | 솔루션 | 어떻게 해결할지 한 문장, 최대 세 문장. 검토한 대안 목록은 넣지 않음 |

| 8 | 구현 상세 | 번호, 진입점, 화면, 기능, 요구사항 5열 표. 기능 하나가 한 행. 화면 열에 신규 생성인지 기존 화면 수정인지 표기. 요구사항 셀은 번호 불릿. 확인 사항은 그 셀 안에 ⚠️와 결정 주체. 상태 전이나 API 순서가 있으면 해당 행 아래에 다이어그램(그림) |
| 9 | 제약과 참고 | 자유 서술 한 단락과 링크 |

제거: 페르소나 시나리오, 시나리오 표와 오류 등급, 성공 기준과 배포 차단 조건, 향후 방향, 미팅록, 업데이트 로그, 플랫폼별 UX 표(제약에 한 줄로), 변경유형 열, "맥락:" 라벨, "확인이 필요한 항목" 별도 섹션(⚠️ 인라인으로 대체), 대안 검토 표

기준 샘플: `docs/samples/2026-09-17-sample-preferred-location.md` (레포 미포함, 로컬 전용). 스킬의 `references/template.md`에는 가상의 예시로 같은 밀도를 보여줌

## 다이어그램 파이프라인

### 판정 규칙

- 분기가 2개 이상인 사용자 흐름: flowchart. 방향은 TD 기본
- 상태가 바뀌는 기능(신청, 승인, 만료 등): stateDiagram-v2
- 클라이언트, 서버, 외부 API 호출 순서가 구현에 중요한 경우: sequenceDiagram
- 노드 텍스트는 12자 이내. 넘으면 용어 표의 짧은 용어로 바꿈

### 생성

- 코드를 `docs/diagrams/{이름}.mmd`로 저장
- `npx -y @mermaid-js/mermaid-cli -i {이름}.mmd -o {이름}.png -b white` 로 렌더. 검증 완료(2026-09-17, Node 23, 한글 정상)
- 첨부 이미지용: `-w 1200 -s 2`. 다이어그램 블록용: `-w 300 -s 2` (블록이 폭 300px로 표시하므로 2배 해상도로 선명하게)
- 렌더 실패 시 코드를 접힘 블록으로 넣고 ⚠️ 표시. 실패를 조용히 넘기지 않음

### 삽입 경로 1. 첨부 이미지 (기본)

- 환경변수 `ATLASSIAN_EMAIL`, `ATLASSIAN_API_TOKEN`, `ATLASSIAN_SITE`(기본 `wantedlab.atlassian.net`)를 읽음
- 없으면 발급 안내를 한 번 출력하고 경로 2로 진행. 안내 내용: id.atlassian.com의 API 토큰 페이지에서 발급, 셸 환경변수로 등록, 토큰은 본인 것만 사용
- 업로드: `POST /wiki/rest/api/content/{pageId}/child/attachment`, 헤더 `X-Atlassian-Token: nocheck`, Basic 인증(이메일:토큰), multipart 파일
- 응답의 미디어 ID와 컬렉션(`contentId-{pageId}`)으로 본문에 `media-single` figure를 넣음. 폭은 percentage 80 (⚠️ 응답 필드에서 미디어 ID를 어디서 읽는지 구현 시 실측 확인)
- 같은 이름의 첨부가 이미 있으면 새 버전으로 올림 (`/child/attachment/{attachmentId}/data`)
- 페이지가 아직 없으면 먼저 페이지를 만들고 pageId를 받은 뒤 첨부와 본문 갱신을 이어서 함

### 삽입 경로 2. 다이어그램 블록 (토큰 없을 때)

- `data-extension-key="mermaid"`, `data-extension-type="com.atlassian.confluence.macro.core"` 확장 div를 HTML 본문에 넣음
- macroParams: size(medium), isEditable(true), diagramCode(코드), caption, theme(default), lastEdited(ISO 시각), diagramType(mermaid), `__bodyContent`(PNG base64). macroMetadata: schemaVersion 1, placeholder 아이콘 URL, title "Mermaid chart"
- 검증 완료(2026-09-17): 코드와 PNG를 함께 넣으면 보기 화면에 그림 표시. 코드만 넣으면 빈칸. size 값은 표시 크기에 영향 없음. 표시 폭은 약 300px
- 이 경로로 넣었을 때는 게시 안내에 "그림이 작게 보이면 토큰을 등록하면 크게 들어갑니다" 한 줄을 붙임

### 로컬 문서

- `docs/PRODUCT_SPEC.md`에는 `![](diagrams/{이름}.png)`로 그림을 넣고, 코드는 넣지 않음

## 리뷰 체크리스트와 질문 매핑

- `references/review-checklist.md`: req-review의 checklist.md를 그대로 가져옴. 별도 스킬(req-review)과 파일을 공유하지 않고 복제함 (스킬 갱신이 SKILL.md 단위라 외부 의존을 두지 않음)
- `references/question-map.md`: 대항목, 소항목, 질문 문안, 답이 들어갈 섹션과 셀, 문서 유형별 적용 여부를 표로 정의
- `references/writing-style.md`: `~/writing-rules/` 02, 04, 05의 핵심(금지 기호, 금지어와 치환, 개조식 종결, 근거 붙이는 법)을 스킬 안에 복제. 전사 배포 환경에는 원본 폴더가 없음
- 예: "권한별 접근 범위" 미정의 → 질문 "이 화면은 어떤 유저 유형에게 보이나요? (선택: 전체, 로그인 유저, 기업 회원, 기타)" → 구현 범위 요약의 메뉴 구조 표 "노출 조건" 셀
