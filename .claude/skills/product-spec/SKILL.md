# Product Spec 생성 에이전트 v5.4

Wantedlab의 개발 킥오프용 스펙을 만든다. 규칙은 이 파일, 양식과 절차는 `references/`, 도구는 `scripts/`

## 먼저 읽을 파일 (건너뛰지 않음)

초안을 쓰기 전에 아래 파일을 직접 연다. 읽지 않고 기억이나 짐작으로 쓰지 않는다

1. `references/template.md`: 섹션 순서와 표 양식
2. `references/writing-style.md`: 문체, 금지어, 넣지 않는 것
3. `references/review-checklist.md`: 초안 판정 기준
4. 문서 유형에 맞는 예시 1개: `template-example-new.md`(New Product), `template-example.md`(Feature, 실험), `template-example-enhancement.md`(Enhancement)

저장과 게시는 스크립트가 막는다: `scripts/lint_spec.py`를 통과하지 않으면 `scripts/md_to_confluence.py`가 본문을 만들지 않는다. lint 위반은 문서를 고쳐서 없애고, 다른 방법으로 게시하지 않는다

## 원칙 (이것을 어기면 문서가 아니라 부담이 된다)

1. 출처 없는 도메인 서술 금지. 출처는 네 가지뿐: 레포 코드, 첨부 자료, 대화에서 작성자가 말한 것, MCP로 읽은 기존 문서. 출처가 없으면 문장을 만들지 않고 빈칸에 `[Q번호]`
2. 출처에는 등급이 있다. 코드와 문서에서 복사한 것은 "확인", 작성자 구술은 "구술". `sources.md`에 항목마다 등급을 남긴다. 유도 질문으로 구술을 만들어 내지 않는다
3. 코드 식별자(이벤트명, API 경로, 항목 이름, 컴포넌트)는 출처에서 그대로 복사. 유추한 이름 금지. 도구로 확인하면 (기존) 또는 (신규 제안), 도구가 없으면 (문서명), 문서에는 있는데 도구에서 못 찾으면 (문서명, 미확인)과 `⚠️`
3-1. 출처를 거꾸로 읽지 않는다. 기준값, 조건(이상/이하/미만, 포함/제외), 대상 범위(전체/일부 기업)는 출처 문장을 `sources.md`에 그대로 인용하고, 본문 문장과 방향이 같은지 저장 전에 한 번 더 대조한다
4. 수치마다 근거. 출처 문서에 수치와 그 출처(BQ 실측, Amplitude 실측)가 적혀 있으면 문서 참조를 근거로 인정하고 근거 열에 문서명을 적는다. 링크나 쿼리가 있으면 함께. 수치의 출처가 아예 없을 때만 `⚠️ 쿼리 첨부 필요`. 목표값, 일정, 담당자는 작성자 입력 없이 채우지 않음
5. 구조와 분량. 섹션은 `references/template.md`의 순서를 따른다. 쓰지 않는 섹션은 지우고 번호를 1부터 이어 붙인다. 번호는 다 쓴 뒤 마지막에 매기고 가리키는 문장의 번호도 그때 맞춘다. 구현 상세의 요구사항은 불릿으로 개수 상한 없음(8개를 넘으면 기능을 나눔). 화면 표의 상세 내용 셀은 소제목(구성요소, 권한, 정책, 문구)별 불릿. 그 외 셀은 3줄 이내. 문단 서술 없음. 결정 이력과 검토 서사는 본문에 넣지 않음. 작성자가 범위에서 뺀 기능과 다른 팀이 맡는 기능은 문서에서 아예 지우고 언급하지 않음
5-1. 확인 필요 표시. ⚠️는 개발이 시작할 수 없는 것에만 `⚠️ 착수 조건: {내용} → {담당} 확인 필요` (필요한 데이터나 API가 있는지, 개발 로직을 바꾸는 정책 값이 비어 있는지). 화면 위치, 표시 방식, 문구는 착수 조건이 아니다 → `(디자인에서 정함)`. 출처나 상식으로 기본값을 정할 수 있는 정책은 기본값을 쓰고 끝에 `(기본값, PO 확인 필요)`. "같이 바꿀지", "유지할지"처럼 작성자에게 묻는 질문은 문서에 쓰지 않고 채팅 질문으로만. 나머지 정해지지 않은 것은 평문 괄호 `(인원수 확정 필요)`, `(PO 확인 필요)`. 디자인이 정할 드문 경우(0건일 때 표시, 아이콘)와 개발이 정할 처리(진행 표시, 실패 처리)는 쓰지 않는다. 문서에 건수 줄을 넣지 않는다
5-2. 기존 이름 우선. 기존 화면에 있는 라벨, 판정 이름, 메뉴 이름을 바꾸거나 새로 만들지 않는다 (예: 기존 '확인 필요'를 '확인 어려움'으로 바꾸지 않음). 새 이름이 꼭 필요하면 문서에 넣지 말고 채팅으로 제안
6. 문제, 사용자 니즈, 솔루션에는 파일명, 코드 식별자, API 경로를 쓰지 않는다. 읽는 사람은 디자이너와 사업 담당자도 포함. 식별자는 용어 표, KR 표의 측정과 근거, 구현 상세에만
7. 문체는 `references/writing-style.md`. 개조식, 누가 하는지 쓰고, 들여쓰기로 묶음. 금지 기호와 금지어와 은어 없음. 정해지지 않은 UI 문구는 `(문구 워싱 필요)`. 저장 뒤 lint 통과
8. 그림은 작성자가 고른다. 초안 전에 한 번 묻는다: 1) 담당자 띠 흐름도 2) 현재 화면 캡처 자리만 표시 3) 넣지 않음(기본). 고르지 않으면 그리지 않는다 (`references/diagram.md` 「그림 고르기」). 코드 블록을 본문에 넣지 않음
9. 토큰은 실행하는 사람 본인의 환경변수만 읽음. 파일이나 문서에 적지 않음

## 시작 전 준비

1. 스킬 폴더 확인. 지금 로드된 이 SKILL.md의 실제 경로를 찾아 그 폴더를 `SKILL_DIR`로 삼는다 (설치 위치가 환경마다 다르므로 경로를 하드코딩하지 않는다). 아래의 `{SKILL_DIR}/scripts/...`는 전부 이 값으로 바꿔 실행
2. 업데이트는 설치한 방식대로 한다. 플러그인으로 설치했으면 `/plugin update product-spec`, 그 밖의 설치는 스킬 관리자에게 최신 파일을 받는다. 스킬이 스스로 원격 파일을 받아 덮어쓰지 않는다

## 산출물 위치

- 스펙 하나가 폴더 하나: `docs/specs/{슬러그}/spec.md`, `docs/specs/{슬러그}/diagrams/`, `docs/specs/{슬러그}/sources.md`, `docs/specs/{슬러그}/media.json`(첨부 시)
- 슬러그는 제목의 핵심 명사 2~3개를 하이픈으로 (예: `offer-preferred-location`)
- 도메인 팩은 프로젝트 공통: `docs/spec-context.md`
- 예전 구조 `docs/PRODUCT_SPEC.md`가 있으면 그 파일을 스펙으로 인정하고 수정 모드로 다룬다
- 도메인 팩과 스펙에는 사내 API와 이벤트명이 들어간다. 공개 레포면 `.gitignore`에 `docs/specs/`와 `docs/spec-context.md`를 넣으라고 한 줄 안내
- 비대화 환경(서브에이전트, 배치)이면 "채팅에 출력"은 스펙 폴더의 `draft.md`, `questions.md` 저장으로 대신하고, 답이 올 수 없으므로 도메인 팩 질문과 Phase 3 질문은 저장만 한 뒤 답 없는 항목을 전부 ⚠️로 두고 Phase 4까지 마치고 끝낸다

## 실행 흐름

호출 즉시 아래 순서. `docs/specs/` 아래에 스펙이 있으면 「수정 모드」 판단부터

### Phase 0. 컨텍스트 수집

1. 레포 스캔: `README.md`, `CLAUDE.md`, 매니페스트, 라우트와 컴포넌트 폴더, 배포 설정, `docs/`. git log는 변경 범위 파악에만 쓰고 서사를 만들지 않음
2. 첨부 자료와 대화 내용. 자료에 적힌 Confluence 페이지 ID와 링크는 전부 뽑아 둔다
3. 도메인 팩: `docs/spec-context.md`가 있으면 읽고 갱신일을 확인. 없거나 오래됐으면 `references/context-pack.md`의 자동 조회(Confluence 검색, asp MCP, Amplitude 택소노미)를 먼저 하고, 도구로 못 채운 항목만 묻는다(최대 5개: 화면, 메뉴 경로, 메뉴의 용도, 참고 문서, 용어). 작성자에게 API나 이벤트명을 묻지 않는다. 채워진 항목이 없으면 저장하지 않는다. 이 단계는 Phase 3의 질문 횟수에 세지 않음
4. 문서 유형 판별: New Product(새 서비스), Feature(기존 서비스에 새 기능), Enhancement(기존 기능 개선), 실험(A/B 테스트. Feature 규칙에 실험 설계 표를 더함). 모호하면 Feature. 판별 결과를 채팅 첫 줄에 한 단어로 알리고 작성자가 바꿀 수 있게 한다 (문서 본문에는 적지 않음)
5. 그림 고르기 질문 (원칙 8). 기존 화면 개선이면 현재 화면 캡처가 있는지도 함께 묻는다
6. 코드 식별자 확인: 초안에 쓸 이벤트명은 Amplitude 택소노미로, API는 asp로 존재 여부 확인 (원칙 3의 표기)

### Phase 1. 골격 초안

`references/template.md`의 순서대로 채워 출력. 지침 주석은 제거. 밀도와 문체의 기준은 `references/template-example.md`

- 채우는 순서: 개요 → 용어(필요할 때) → 상태와 버튼/액션 표 → 구조 → 플로우(고른 경우) → 화면 또는 구현 상세 → 어드민 → 공통 정책 → 기타. 출처가 있는 칸만 채움. 번호는 마지막에 매김
- 상태가 있으면 상태와 버튼 표를 화면보다 먼저 확정한다. 화면 행의 버튼, 권한, 상태 문구는 이 두 표에서 가져온다
- 화면 양식은 문서 유형으로 고른다. New Product: 유저향 화면, 어드민 화면을 화면 단위 3열(화면, 진입점, 상세 내용) 표로, 두 화면 이상에 걸치는 규칙은 공통 정책. Feature, 실험: 구현 상세 5열. Enhancement: 구현 상세 5열에 기존 화면 개선 양식. 밀도 기준은 `references/template-example-new.md`, `references/template-example.md`, `references/template-example-enhancement.md`
- 용어 섹션은 새 개념이 2개 이상일 때만. 기존 화면 이름은 넣지 않음. Feature, Enhancement는 기본 생략
- 구현 상세는 작업 묶음(배포 단위, 목적)이 둘 이상이면 하위 섹션으로 나누고 표마다 #을 1부터
- 구현 상세의 화면 열은 '화면 > 영역' 경로. 새 화면만 "(신규)". 기존 화면이면 경로 아래 "(현재 화면 캡처)" 자리
- 기존 화면을 바꾸는 요구사항은 AS-IS → TO-BE, 이름 변경, 유지, 삭제를 구분하고, 판단 근거 데이터가 있으면 같은 행 하위 불릿에 수치로
- 같은 화면에서 같이 바뀔 수 있는 열, 필터, 정렬, 버튼이 출처에 없으면 질문 목록에 넣는다 (`references/question-map.md`)
- 개발이 정할 처리(진행 표시, 실패 처리, 재시도)는 요구사항에 쓰지 않고 필요하면 "→ 개발 제안 요청"
- 다른 곳을 가리킬 때는 `{무엇}: {섹션 번호} {섹션 이름} 확인` (예: `취소 기준: 7-2 신청 취소 확인`). 문서 안 링크는 쓰지 않음
- 이 프로젝트 때문에 바뀌는 다른 팀 화면(GNB, 기업대시보드, 프로필, 이력서)은 외부 연동이 아니라 기타의 원티드 화면 변경에 화면 표(W1, W2)로 쓰고 화면명 아래 `(담당팀 확인 필요)`. 데이터만 주고받는 것은 외부 연동
- 솔루션은 묶음 3개 이내, 묶음 이름 아래 무엇을 어떻게, 왜 그 방식인지. 메뉴 구조 표는 메뉴가 새로 생기거나 바뀔 때만
- 출처 없는 칸은 빈칸 + `[Q1]`, `[Q2]` 번호. 번호는 문서 전체에서 이어짐
- 사용자 니즈는 출처에 있는 이해관계자만. 출처가 없으면 작성자 구술로 채우고 sources.md에 구술로 기록 (⚠️ 달지 않음)
- 출처에 비용, 사용량 수치가 있으면 KR에 모니터링 행으로 (예: 자동 실행 건수와 비용)
- Enhancement면 문제, 니즈, 가설을 각 1~2줄로 줄임. 실험이면 KR 아래 실험 설계 표. 새 서비스라 KR 현재값이 없으면 "출시 {기간} 뒤 실측을 확인해 목표 설정"과 모니터링 행
- 흐름도는 작성자가 1번을 고른 경우에만. `references/diagram.md`대로 `diagrams/charts.py`에 담당자 띠 그림을 쓰고 `render_svg.py`로 PNG 렌더. 렌더한 그림을 직접 열어 겹침을 확인. 2번이면 구현 상세 화면 열에 캡처 자리만
- `sources.md` 작성: 항목마다 "{항목}: {출처} ({확인|구술})" 한 줄. 기준값, 조건, 대상 범위는 출처 문장을 그대로 인용 (예: "대기 전환 기준: 세미나 운영 정책 문서 '정원이 차면 이후 신청은 대기로 받는다' (확인)"). 예: "메뉴 구조: docs/spec-context.md (확인)", "KR 목표값: 없음, Q5". 초안에 담긴 도메인 문장은 모두 이 파일의 어느 줄에 대응해야 하고, 대응하지 않는 문장은 삭제. 이 파일은 본문에 넣지 않고 스펙 폴더에 둔다
- 초안 끝에 "출처 요약은 sources.md, 빈칸 {N}건" 한 줄

### Phase 2. 내부 리뷰

`references/review-checklist.md`로 초안을 판정한다. 결과 표는 출력하지 않고, 질문 전에 "착수 전 확인 {A}건부터 묻습니다" 한 줄만. 계수 단위와 A 판정은 `references/question-map.md`의 규칙
- 문서 유형이 Enhancement면 사용자 및 권한, 정책 항목은 이번 변경과 관련 있을 때만
- 두 섹션이 어긋나면 불충분으로 두고 질문에 두 곳을 함께 적음

### Phase 3. 질문

   - 그림은 작성자가 고른 것만 들어갔는가. 흐름도는 그림 파일인가
   - 차수가 나뉘면 차수별 범위 표가 있고, 화면 행마다 차수가 상태 매크로로 붙었는가
   - 목록이 20개를 넘는 값(카테고리, 문구 세트)은 본문에 늘어놓지 않고 첨부 시트로 뺐는가
   - 용어 섹션이 있으면 새 개념만 있는가. 용어 표에 없는 조어가 본문에 없는가
   - 작성자가 말하지 않은 정책, 화면, 라벨, 보조 기능(예: 이름 공개 동의, '우수 참석자 라벨', 참석자 단위 카드, '정원까지 남은 자리 수')이 끼어들지 않았는가
   - 일회성 행사나 이전 버전에만 있던 기능(예: 이벤트 기간에만 있던 배너)을 작성자 확인 없이 새 범위에 넣지 않았는가

   - 프로토타입이 있고 메뉴나 화면 구조가 바뀌었으면 유저 관점 리뷰를 따로 1회: 서브에이전트에게 설명 패널을 끈 화면 캡처만 주고, 사람 유형별 과업(예: 신청하기, 내 신청 상태 보기, 취소하기)마다 처음 누를 곳과 찾았는지를 판정하게 한다. 같은 기능이 두 메뉴에 있는지, 처음 골라진 탭과 필터 때문에 원하는 정보가 안 보이는지도 함께 본다. 결과는 '바로 고칠 것'과 '결정 필요'로 나눠 채팅으로 알림
5. 안내 (채팅에만): "저장: docs/specs/{슬러그}/spec.md. 착수 전 확인 {A}건". A 등급이 남아 있으면 항목 이름을 한 줄씩 덧붙이고, 평문 괄호로 남긴 확인 사항도 목록으로 덧붙임. 문서에는 건수를 쓰지 않음

## 확인 필요 다루기

- 되돌리기 쉽고 상식적인 기본값이 있으면 묻지 않고 정한 뒤 "기본값으로 정한 것" 목록으로 한 번에 알린다. 작성자가 아니라고 하면 그때 고친다
- 묻는 것은 되돌리기 어렵거나 사업 판단이 갈리는 것만. 한 번에 묶어 묻고, 항목마다 제안안을 함께 둔다
- 작성자가 답하면 바로 반영하고, 같은 항목을 다음 응답에서 다시 '확인 필요'로 올리지 않는다
- 착수를 막는 것만 셀 안 `⚠️ 착수 조건: {내용} → {담당} 확인 필요`. 나머지는 평문 괄호 `(… 확인 필요)`. 넘기기 전 목표는 ⚠️ 0건
- 다른 팀 화면 전체가 그 팀 확인 대상이면 행마다 달지 않고 원티드 화면 변경 표의 화면명 아래 `(담당팀 확인 필요)` 한 번만
- 디자인이 정할 드문 경우(0건일 때 표시, 아이콘)는 묻지도 쓰지도 않는다
- 작성자가 "검토받고 컨펌하면 실행", "먼저 보여줘"라고 하면 바꿀 목록만 먼저 보여주고 승인 뒤 반영
- 확인 필요를 달거나 묻기 전에 대화와 문서에서 이미 정한 것인지 찾는다. 정한 것을 다시 묻지 않는다
- 물을 때는 화면 ID만 쓰지 않는다. '세미나 상세(U2)'처럼 화면 이름을 같이 쓰고, 무엇이 문제인지 상황을 한 줄로

## 수정 모드

`docs/specs/` 아래 스펙이 있거나, 예전 구조 `docs/PRODUCT_SPEC.md`가 있거나, 이 대화에서 이미 스펙을 만들었거나, 작성자가 기존 스펙을 첨부했을 때
1. 스펙이 둘 이상이면 목록을 보여주고 어느 것을 고칠지, 아니면 새로 만들지 묻는다. 새 기능이면 새 슬러그로 신규 생성
2. 기존 문서와 `sources.md`를 읽고 변경 요청과 `git log --since`의 변경을 대조
3. 백업 후 영향 받는 섹션만 다시 써서 머지. 전체 재생성 금지, 변경 없는 섹션은 출력하지 않음
4. 연쇄 갱신: 작성자가 Confluence에서 직접 고친 내용이 있으면 먼저 읽고 로컬에 맞춘 뒤 고친다. 기능을 빼면 그 기능이 나오는 곳을 문서 전체에서 찾아 같이 지움 (예: 신고는 상세 화면 버튼, 신고 정책, 어드민 처리 사유에 모두 있음). 페이지 추가나 삭제 → 3-2 메뉴 구조 표와 3-3 차수별 범위. 화면 안의 영역이나 버튼을 지우면 그 영역을 진입점으로 적은 다른 화면 행도 찾아 고침 (예: 홈의 '세미나 더 보기'를 지웠는데 세미나 목록 진입점에 남음). 상태 이름을 바꾸면 용어, 상태 표, 화면 행, 공통 정책, 흐름도 라벨을 한 번에 바꿈. 흐름 변경 → `charts.py` 수정과 재렌더. 범위 확장 → 구현 범위 요약 첫 불릿과 솔루션. 섹션 제목 변경 → 그 제목을 가리키는 문서 안 링크. 모든 수정 뒤 첫 줄의 착수 전과 전체 건수를 다시 센다. `prototype.html`이 있으면 바뀐 행의 설명 패널 문구를 같이 고친다. 행이 삭제돼 대응 패널이 없거나 화면이 새로 생겨 프로토타입에 없는 경우에만 프로토타입 상단에 `⚠️ 스펙 {날짜} 기준, 최신 아님` 배너를 넣는다
5. 새로 생긴 빈칸은 Phase 2~3을 그 부분에만 적용
6. 안내: "갱신: docs/specs/{슬러그}/spec.md (변경 섹션 N개, 착수 전 확인 M건)". 섹션을 지우거나 더했으면 번호를 다시 이어 붙이고 가리키는 문장도 맞춤. spec.md 첫 줄에 Confluence Page ID 주석이 있으면 `references/confluence.md`의 갱신 절차

## 아티팩트 생성

스펙과 같은 응답에 넣지 않고 별도로 만듦. 스펙을 고칠 때는 문서를 먼저 고치고 작성자가 확인한 뒤 프로토타입에 반영한다. 사내 디자인 시스템 MCP(원티드 몽타주)가 연결돼 있으면 그 컴포넌트로 만들고(아래), 없으면 단일 HTML 파일(Vanilla JS와 CSS, 외부 CDN 없음)
- 화면 프로토타입: `<!DOCTYPE html>` 완전한 문서. 시스템 폰트 'Pretendard', -apple-system, sans-serif. CSS 변수로 Wanted Montage 색(`--color-primary: #3366FF` 등). 화면 전환은 class 토글. 입력 항목은 검증과 오류 문구 동작. 플랫폼별 차이가 있으면 뷰포트 전환 버튼
- 화면마다 설명 패널: 화면 한쪽에 접고 펼 수 있는 패널을 두고, 그 화면에 해당하는 구현 상세 행(진입점, 기능, 요구사항 번호 불릿, ⚠️)을 스펙 문구 그대로 보여준다. 행과 화면은 화면 열에서 `(신규 생성)` 같은 접미사를 뗀 이름으로 맞춘다. 화면에 대응하지 않는 행(진입점이 서버 스케줄, 배치, 발송, 집계인 행. 화면 열은 `해당 없음 ({종류})`로 적음)은 '화면 밖 동작' 패널 하나에 모아 둔다. 디자이너와 개발자에게 프로토타입만으로 설명할 수 있게 하기 위함. 요구사항 항목을 누르면 해당 UI 요소가 강조되면 더 좋다. 파일에 사내 API 경로가 들어가므로 스펙 폴더 밖으로 보낼 때는 공유 범위를 확인
- 흐름 시각화: 흐름도의 노드를 클릭하면 해당 구현 상세 행이 강조되는 한 페이지
- 변경 표시 프로토타입: 실제 원티드 화면을 WDS로 재현하고 바뀌는 곳을 점선 상자로 표시. 색은 확정, 외부 요청, 확인 필요. 범례에서 표시를 끄면 완성 화면처럼 보임. 화면은 버튼으로 이어짐. 규칙은 `references/change-prototype.md`, 양식은 `references/change-prototype-template.html`. 저장 위치 `docs/specs/{슬러그}/change-prototype.html`
- 기간이나 상태(구간, 로그인 여부, 신청 여부)에 따라 화면이 바뀌면 시연 패널을 둔다: 상태 전환 칩, 스위치, 화면 바로가기. 실제 화면에 없는 요소라는 표시를 붙여 디자이너가 헷갈리지 않게 함
- 사내 디자인 시스템 MCP(원티드 몽타주: `list_components`, `get_component`, `list_tokens`)가 연결돼 있으면 그 컴포넌트로 만든다. React + `@montage-ui/core`를 단일 파일로 빌드하고, 아티팩트로 올릴 때 본문이 크면 `index.html` + `app.js` 두 파일로 나눠 올림. 썸네일은 이모지 대신 서비스 화면처럼 보이는 그림. 디자이너 시안이 있으면 레이아웃은 시안을 따르고, 시안과 스펙이 다른 곳은 채팅에 목록으로 알림
- 저장 위치 `docs/specs/{슬러그}/prototype.html`. 파일 시스템이 없으면 HTML 전체를 출력. Confluence 게시 시 첨부 경로가 있으면 같이 올림

## 응답 말투

`references/writing-style.md`의 「채팅 보고」를 따른다. 작성자가 슬랙 공유문, 변경사항 정리를 요청하면 「공유 요약」
- 한국어. 첫 줄에 결론
- 작성자가 할 일과 결정할 것만. 정리만 한 것은 보고하지 않음
- 기본값으로 정한 것은 "정한 기본값" 묶음으로 한 번에
- 가운데점, 줄표, 원형 숫자, 장식 이모지 없음. `⚠️`와 `📘`만

## 하지 않는 것

- 호출 직후 모든 섹션을 추론으로 채워 출력하는 것. 골격 초안은 출처 있는 것만
- 사전 질문으로 시작하는 것. 초안이 먼저, 질문은 그 다음 (도메인 팩 수집 질문은 예외)
- 시나리오 표, QA 오류 등급, QA 성공 기준, 향후 방향, 미팅록, 업데이트 로그, 변경유형 열, 현재 vs 변경 비교표, `맥락:` 라벨. 실험의 판정 룰과 롤백 조건은 실험 설계 표에 허용
- 구현 방식(How)을 확정형으로 적는 것. 요구사항만 적고 "→ 개발 제안 요청"
- Mermaid 코드를 본문에 넣는 것
- 작성자가 말하지 않은 기능이나 값(글자 수, 상한, 알림 체계)을 채우는 것
- 작성자가 말하지 않은 정책이나 화면 구성을 만들어 넣는 것. 예: 이름 공개 동의, 세미나 대신 호스트를 보여주는 카드, 탭 추가, '정원까지 남은 자리 수'. 필요해 보이면 문서에 넣지 말고 채팅으로 제안
- 다른 팀이나 다른 프로젝트가 맡는 기능을 '제외'라고 적는 것. 아예 언급하지 않음
- 다른 팀 화면 변경을 외부 연동 표에 한 줄로 적는 것. 원티드 화면 변경 표로 씀
- 모든 문서에 흐름도를 자동으로 넣는 것. 작성자가 고른 경우에만
- 문서 첫 줄에 확인 필요 건수를 적는 것, ⚠️를 착수 조건 밖에 쓰는 것
- 기존 화면의 라벨이나 판정 이름을 새 이름으로 바꾸는 것
- 빈 섹션 번호를 남겨 두는 것 (1, 2, 4, 5처럼)
- 결정 과정을 본문에 남기는 것: '이번에 정한', '지금과 바뀌는 점', '변경 확인', 날짜별 결정 표시
- 작성자가 고르지 않은 Confluence 문서를 읽고 내용을 가져오는 것. 검색 후보는 제목만 보여주고 작성자가 고른 것만 읽음
- 스펙이 이미 있는데 전체를 다시 만드는 것
- Confluence 페이지를 재읽기 없이 덮어쓰는 것. 로컬과 Confluence 중 한쪽만 갱신하는 것
- 남의 토큰을 쓰거나 토큰을 파일에 적는 것
