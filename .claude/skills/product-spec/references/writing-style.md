# 문체 규칙

스킬이 만드는 스펙 본문, 채팅 안내, 스크립트가 출력하는 문자열 전부에 적용. 판정은 `scripts/lint_spec.py`로 자동 검사하고, 검사에 안 걸리는 항목은 아래 규칙으로 직접 확인

## 기호

| 금지 | 대체 |
|---|---|
| 가운데점 `·` | 슬래시 `/` 또는 쉼표 |
| 줄표 `—` `–` `ㅡ` | 쉼표, 콜론, 화살표 `→` |
| 원형 숫자 `①②③` | `1.` `2.` `3.` |
| 장식용 구분선 | 쓰지 않음 |
| 서술 강조용 큰따옴표 | 작은따옴표 또는 굵게 |

- 인과와 변화는 `→`, 증감은 `(+2.02%)` 또는 `129,273 → 150,478`
- 이모지는 기능 마커만. `⚠️` 논의 및 결정 필요, `📘` 구간 구분, 표 안의 해당 여부 표시에 `✓`. 실제 UI 카피의 아이콘은 예외

## 끝 온점

- 개조식 명사 종결에는 마침표 없음
- 완결문(`~다`, `~한다`, `~것이다`)에만 마침표
- 문장을 나누는 중간 마침표는 허용 ("막음. 관리자는 항상 1명 이상")

## 금지어와 치환

| 금지 | 대체 |
|---|---|
| `미결, 미결 사항` | 논의 및 결정 필요한 사항 |
| `누락` | 빠진 항목 |
| `누수` | 정보가 밖으로 나감, 비용이 새는 문제 |
| `선제, 선제적` | 미리 |
| `고지` | 알림, 안내 |
| `제고` | 높임, 개선 |
| `도모` | 추진, 시도 |
| `진행하다` | 하다 |
| `요건` | 필요한 조건 |
| `상기` | 위에 적은 |

상투 어휘 금지: 기반, 관점, 측면, 원활한, 효과적인, 체계적인, 필요시, 향후, 관련하여, `~될 수 있다`, `~되어야 한다`, `~로 판단된다`, 근거 없는 "중요합니다", "필수적입니다"

공문서체 금지: `하였습니다`, `되었습니다`, `따라서`, `그러므로`, `아울러`, `귀하`

기존 문서에서 이어받은 표현이라도 다시 판단. 그대로 복사하지 않음

## 종결

- 90%는 개조식. 명사 종결 또는 `~없음`, `~함`, `~불가`, `~신설`. 평서형(`~한다`, `~이다`)은 도입부와 판단 근거 등 10%
- 서술어는 명사로 닫음. "정리한다" → "정의 필요", "확인해야 한다" → "확인 필요", "작성하지 못한다" → "작성 불가"
- 격식 개조식. 구어체 축약(씀, 봄, 뜸, 안 함, `~임`) 금지. "구직자임" → "구직자"
- `~습니다`체 본문 금지
- 캐주얼 표현 금지. "낱개로 던짐" → "개별 단위로 제시"
- 예외: 실제 UI 카피와 유저 인터뷰 인용은 원문 톤 유지 ("~해도 상관없어요")

갈래
- 배경과 서술: 명사형 개조식
- 목표와 지시: `한다`체
- 가설: `~것이다`체
- UI 카피와 유저 인용: 존댓말 원문

## 문장 구성

- 주어와 행위 주체 생략. "리드 4곳에서 구매 문의가 들어왔으나" 같은 주어 서술 구조 금지
- 근거는 앞에 수식구로, 결론은 뒤에. "AX 챔피언 기업 미팅에서 확인된 니즈로 / 제품 방향성 정의 필요". 접속어(`~했으나`)로 잇지 않음
- 한 줄에 정보 하나
- 추측 어미 대신 사실
- 볼드는 항목 제목에만
- 문서 자기소개와 메타 서술 금지. "이 문서는 정본 Spec"류 문장 없이 본문부터 시작
- 표 중심. 셀 안은 불릿 2~3단. 문단 서술 최소
- 표 셀 안에서 문장을 마침표로 잇지 않는다. 정보가 둘 이상이면 불릿으로 나누고, 앞 항목에 딸린 내용은 한 단계 아래 불릿으로 단다 (lint가 잡음)
  - 나쁨: `| 정원 | 팀장 포함 5명. 프로그램 서비스는 설정값 (5명 이하) |`
  - 좋음: `| 정원 | - 팀장 포함 5명<br>- 프로그램 서비스는 설정값 (5명 이하) |`
  - 딸린 내용: `- 반려: 사유 필수<br>  - 검수 중 → 작성 중<br>  - 내 서비스에 사유 표시`
  - 따옴표 안의 실제 UI 문구는 마침표가 있어도 그대로 둔다
- 폐기된 안, 취소선 이력은 쓰지 않음

## 제목

- 섹션, 소제목, 그림 제목은 기능이나 규칙 이름 그대로. "팀 초대 플로우", "추천", "순위"
- 수사형 제목 금지: "등록부터 뱃지까지", "한눈에 보는 ~", "~의 모든 것"
- 질문형 제목 금지

## 구조 설명

- 개념은 유저가 화면에서 보는 것으로 설명. 추상어 대신 "어디에 올리고, 어디에 보이고, 무엇이 따로인지"
  - 나쁨: "hub 안에 상시 공간과 프로그램 공간이 공존하는 이중 구조"
  - 좋음: "상시: 언제든 서비스를 올리는 곳. hub 서비스 목록에 쌓임" / "프로그램: 해커톤처럼 기간이 정해진 행사마다 따로 생기는 곳. 그 안에서만 보임"

## 은어

읽는 사람이 쓰는 말로 적는다. 아래는 `scripts/lint_spec.py`가 잡는다. `필드`는 API 표와 이벤트 표에서 정확한 말이라 허용하고 화면 입력은 `항목`으로, `맥락:` 라벨만 금지, `액션 시트`는 컴포넌트 이름이라 허용

검사가 틀렸다고 판단되면(예: 실제 UI 카피, 컴포넌트 이름) 그 줄 끝에 `<!-- lint-skip: 은어 -->`처럼 건너뛸 검사 종류(은어, 금지어, 행 번호 참조, 습니다체, 이모지)를 적는다. 그 종류만 건너뛰고 나머지 검사는 그대로. 종류 없이 `lint-skip`만 쓰면 그 줄 전체를 건너뛰므로 쓰지 않는다

| 쓰지 않음 | 씀 |
|---|---|
| `전이, 상태 전이` | 상태가 바뀌는 때 |
| `액션` | 동작 |
| `인터페이스` | 넘기는 방법 |
| `카운터` | 세기 |
| `플래그` | 표시 |
| `스냅샷` | 그 시점 값을 따로 저장 |
| `마이그레이션` | 데이터 이관 |
| `엣지 케이스` | 드문 경우 |
| `밸리데이션` | 검사 |
| `큐` | 대기 목록 |

문서 안에서만 쓰는 말을 새로 만들면 반드시 용어 표에 넣는다. 용어 표에 없는 조어는 쓰지 않는다

## 문서 안에서 다른 곳 가리키기

섹션 번호와 섹션 이름을 함께 쓴다. 문서 안 링크(앵커)는 쓰지 않는다

- 꼴: `{무엇}: {섹션 번호} {섹션 이름} 확인`
  - 예: `순위 기준: 7-2 순위 표 확인`, `팀 규칙: 7-6 팀 표 확인`
- 링크를 쓰지 않는 이유: Confluence 앵커는 제목이 바뀌거나 페이지를 복사하면 깨지고, 깨져도 겉보기로 알 수 없음. 번호와 이름을 같이 쓰면 회의에서도 "7-2 봐주세요"로 부를 수 있음
- 섹션을 끼우거나 빼서 번호가 바뀌면, 그 번호를 가리키는 문장을 전부 찾아 같이 고친다

행 번호로 가리키지 않는다. 구현 상세는 행이 자주 늘고, 행 하나가 끼면 문서 전체의 참조가 어긋난다. 읽는 사람도 표에서 번호를 세어야 한다

| 쓰지 않음 | 씀 |
|---|---|
| `전이는 구현 상세 14행` | (용어 칸 안에서 뜻을 끝냄) |
| `15행 10번 규칙` | 서비스 등록 화면의 삭제 규칙 |
| `접수 조건(11행 4번)` | 조건을 그 자리에 한 줄로 다시 씀 |
| `9-1의 마감 잠금보다 우선` | 서비스 등록 화면의 마감 뒤 수정 잠금보다 우선 |

- 화면 이름은 바뀌지 않고 검색으로 바로 찾힌다. 구현 상세의 화면 열에 그대로 있다
- 한 줄로 다시 쓸 수 있으면 가리키지 말고 그 자리에 쓴다
- 같은 행 안에서 번호로 가리키는 것(같은 셀의 "4번 참고")은 허용

## 용어 표 구성

- 일반 용어는 그룹 없이 표 하나 (서비스, 등록 위치, 소유자, 검수, 뱃지 등)
- 상태와 버튼은 따로 표로 묶는다. 읽는 사람이 상태와 버튼을 한눈에 대조할 수 있게 하기 위함
  - 상태 표: 상태, 뜻, 누가 봄, 쓸 수 있는 버튼
  - 버튼/액션 표: 버튼, 누르는 때, 누르면
- 특정 기능에만 쓰는 용어 묶음(예: 프로그램 일정)은 소제목 하나로 따로 둬도 됨
- 그룹 이름을 억지로 만들지 않는다 ("서비스와 공간" 같은 이름은 쓰지 않음)

## 용어 표는 자기완결

용어 칸에서 뜻이 끝나야 한다. 다른 섹션을 봐야 뜻을 아는 항목은 용어에 넣지 않는다

- 나쁨: `서비스 상태 | 작성 중, 검수 중, 공개, 삭제 4가지. 바뀌는 조건은 구현 상세 14행`
- 좋음: `서비스 상태 | 작성 중(소유자와 팀원만 봄), 검수 중(공개를 기다리는 중), 공개(누구나 봄), 삭제(되돌릴 수 없음)`

값이 바뀌는 조건과 화면 동작은 용어가 아니라 구현 상세에 둔다. 용어에서 그쪽을 가리키지 않아도 읽는 사람은 화면 이름으로 찾는다

## 내부 조어와 영어 혼용

읽는 사람은 디자이너와 개발자. 추상 조어와 영어가 한 줄에 몰리면 낯섦이 겹침

| 쓰지 않음 | 씀 |
|---|---|
| 축(axis) | 그룹 종류, 기준 |
| 헤더 카피, 서브카피 | 제목 문구, 설명 문구 |
| 신호(signal) | 묶는 근거가 되는 유저 행동(찜, 열람, 검색) |
| 실현 시점(Phase 1/2) | 적용 단계(Phase 1/2) |

- 데이터, 실험, 모델 용어(홀드아웃, 증분, 카니발라이제이션 등)는 쉬운 말로 풀고, 반복되면 용어 표에 모음
- 사내에서 실제로 쓰는 이름 사용. "리드" 대신 "AX 챔피언 기업"

## AI 말투 피하기

작성자가 "AI 말투 같다"고 고친 표현들의 공통점. 아래 꼴이 보이면 쉬운 말로 풀어 쓴다

| 특징 | 예 (쓰지 않음) | 씀 |
|---|---|---|
| 한자어 두 글자로 줄인 명사 | 등록 상한, 반려 이력, 노출 여부 처리 | 최대 등록 수, 반려된 적이 있는, 보이게 할지 |
| 상황을 요약하는 말 | 활동이 끊김, 흐름이 단절됨 | 무엇이 안 되는지 그대로 ("새로 올릴 곳이 없음") |
| 없는 라벨을 새로 만듦 | 선정 라벨, 선정자, AI Builder 카드, 개입 동작 | 이미 있는 이름 (Top 10 뱃지, 인기 AI Builder, 7/23 배포) |
| 결정 과정을 남기는 말 | 이번에 정한, 지금과 바뀌는 점, 변경 확인 | 최종 내용만 |
| 전문용어로 뭉뚱그림 | 느슨한 정의, 상태 전이 | 실제 동작 ("ai가 들어간 단어까지 걸릴 수 있음", "상태가 바뀌는 때") |
| 평가하는 수식어 | 핵심, 진짜, 성공적인, 함정 | 사실과 할 일만 |

- 새 단어를 만들고 싶으면 먼저 화면에 실제로 보이는 이름이 있는지 찾는다. 없으면 용어 표에 넣고 작성자에게 이름을 확인받는다

## 근거 붙이는 법

- 주장마다 데이터 링크(Amplitude, BigQuery)와 수치를 본문에 직접
- 지표는 표로. 현재, 목표와 근거 열
- 요구사항마다 왜 하는지 한 줄 (근거가 있을 때만)
- 임계값은 숫자로
- 확정되지 않은 것은 A안, B안을 나열하지 않고 해당 셀에 ⚠️와 결정 주체
- 근거는 라벨 없이 결정에 직결되는 것만 셀 끝에 한 줄. `맥락:` 같은 라벨 금지

## 스펙 고유 규칙

- 디자인과 개발이 바로 착수 가능한 상세도. 화면 구성, 인터랙션, 데이터와 항목, 예외까지
- 작성자가 말하지 않은 기능, 값은 넣지 않음. 글자 수, 상한, 기한 같은 값은 작성자가 준 것만. 디자인에 따라 바뀔 값은 '(디자인 확인 후 변경 가능)'
- 작성자가 범위에서 뺀 기능은 '하지 않음'으로도 적지 않음. 문서에서 아예 지움
- 확인 사항은 해당 기능 옆에 인라인 `⚠️` + 결정 주체 ("⚠️ 개발 확인 필요", "→ 마케팅팀 확인 필요"). 별도 섹션 없음. 라벨은 '논의 및 결정 필요한 사항'
- 넣지 않는 것: 시나리오, QA 등급, 데이터 모델, 미팅록, 업데이트 로그, 변경유형 열, Component 분리 표, 현재 vs 변경 비교표, 기존과 달라지는 점을 적은 문장('기존 ~를 ~로 변경'), 이번에 정한 내용 같은 결정 표시
- 구현 방식(How)은 확정형으로 적지 않음. 충족할 요구사항(What)만 적고 방식은 "개발 제안 요청"으로 염. "요구사항: ~할 것 ⚠️ 방식은 개발 제안으로 결정"
- 지표는 Primary만 두지 않음. Secondary(선행 지표)와 Guardrail을 함께
