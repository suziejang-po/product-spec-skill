# 데이터 근거와 숫자 검증

스펙에 들어가는 수치를 어디에, 어떤 꼴로 쓰고, 넣기 전에 무엇을 확인하는지. 예시는 모두 가상 값

## 본문과 블록 나누기

- 본문에는 값과 무엇의 수치인지만 쓴다
  - 나쁨: `- 결과를 받기까지 평균 약 19일 (BQ 실측, 6~8월 지원 280,713건, 연동 기업 제외)`
  - 좋음: `- 결과를 받기까지 평균 19일`
- 기간, 모수, 제외 조건, 쿼리, 차트 링크는 그 섹션 끝 데이터 근거 블록에
- 수치가 있는 섹션(문제, 원인 가설, KR, 구현 상세의 하위 섹션)마다 블록을 둔다. 주제가 둘이면 블록도 둘
- 코드 블록은 이 블록 안에만

## 데이터 근거 블록 형식

마크다운은 `<details>`로 쓰고, 변환기가 Confluence 펼치기로 바꾼다

~~~
<details>
<summary>데이터 근거: {주제}</summary>

- {요약 1~3줄}

| 항목 | 값 | 기준 |
| --- | --- | --- |
| {무엇의 수치} | 12.8% (200건 / 1,558건) | 지원 건 1,558건 (9/1~9/30 기준) |

- 집계 조건
    - 조회일: {YYYY-MM-DD}
    - {대상, 제외 조건, 시간대 기준}
    - {Amplitude 차트 링크}

```sql
{쿼리 원문}
```

</details>
~~~

- 제목은 `데이터 근거: {주제}`. 주제는 그 블록이 받치는 본문 내용 그대로 (예: `데이터 근거: 결과 대기 일수`)
- 순서는 요약 불릿 1~3줄, 데이터 표(항목, 값, 기준), 집계 조건과 쿼리
- 비율에는 분자와 분모를 같이: `12.8% (200건 / 1,558건)`
- 기간은 `{대상} N건 (M/D~M/D 기준)` 꼴, 집계 조건에 조회일
- 한 표에 기준 기간이나 모수가 다른 숫자가 섞이면 행마다 기준 칸을 따로 채운다. 같으면 같은 값을 그대로 적는다 (빈칸 두지 않음)
- 구간을 나눈 비율의 합이 100%가 아니면 나머지가 무엇인지 한 행 더 적는다 (예: `기타 (판정 없음) 3.1%`)
- 쿼리나 링크가 아직 없으면 집계 조건 끝에 `(쿼리 첨부 필요)`

## 기준값 근거

- 임계치, 기간, 횟수 같은 기준값 옆에는 괄호로 근거를 쓴다
  - 예: `7일 (서류 합격의 85%가 7일 안에 처리되므로)`
- 근거 데이터 표는 게시 뒤 그 기준값 문구에 인라인 댓글로 단다 (`references/confluence.md` 「수치 인라인 댓글」). 댓글이 표를 받지 않으면(400) "{항목}: {값} ({기준})" 불릿으로 바꿔 단다. 본문 근거 블록에도 같은 표를 둔다
- 기준값이 다른 설정과 만나 뜻이 바뀌는지 확인한다
  - 예: 항목이 3개면 비율이 0, 33, 67, 100%만 나와서 '80% 이상'이 '100%'와 같아짐
  - 바뀌면 작성자에게 채팅으로 알리고, 문서에는 실제로 갈리는 값으로 쓴다

## 숫자 검증

스펙에 넣기 전, 수치마다 아래를 확인한다. 결과는 채팅으로만 알린다

- 다시 실행: 쿼리를 다시 돌려 같은 숫자가 나오는지 확인
  - 다시 만들지 못한 숫자는 문서에 넣되, 채팅에 "쿼리 없이 넣은 수치" 목록으로 알린다
- 합계: LIMIT이 걸린 결과나 50행 미리보기를 더해서 합계로 쓰지 않는다. 합계는 쿼리에서 집계
- 분모: 실패 건, 테스트 계정, 제외 대상이 분모에 들어갔는지 확인
- 시간대: 시각 컬럼이 테이블마다 UTC인지 KST인지 확인한 뒤 비교하거나 날짜로 자른다
- 기간: 기간이 다 지나지 않은 건이 분모에 섞이지 않게 한다 (예: 만료 기한이 안 지난 건, 관찰 기간 14일이 안 된 건)
- 해석 범위: 로그가 말하는 범위를 넘겨 쓰지 않는다
  - 나쁨: '열람, 처리 기록 없음'을 '로그인 안 함'으로 씀
  - 좋음: '열람, 처리 기록 없음' 그대로
- 바뀐 숫자: 작성자가 이미 확인한 숫자가 재조회로 바뀌면 채팅에 표로 알린다

~~~
| 항목 | 이전 값 | 바뀐 값 | 이유 |
| --- | --- | --- | --- |
~~~

## 원인 가설 표

문제의 원인이 둘 이상이고 이번 범위에서 고를 때만 둔다. 위치는 문제 바로 아래 '원인 가설'

- 표 위에 우선순위 기준을 한 줄로: 데이터 근거가 있는지, 이번 범위에서 검증할 수 있는지
- 열: 우선순위, 가설, 데이터, 해결책, 이번 차수 포함
  - 데이터 칸은 값만 (건수, 비율). 기준과 쿼리는 그 아래 데이터 근거 블록에
  - 이번 차수 포함 칸은 '포함' 또는 '미포함'
- 우선순위는 이번 차수에서 먼저 검증하는 순서
- 건수가 가장 많은 가설을 미포함으로 두면 표 아래에 이유를 쓴다
- 건수가 적은 가설을 포함하면 표 아래에 'N순위 대비 건수가 적으나 포함하는 이유'를 쓴다
- 데이터로 받쳐지지 않은 가설은 표에서 빼고 아래 '기각할 가설'에 근거와 같이 쓴다
- 표현은 '참고할 만한 데이터', '기각할 데이터'. '버리는 것', '대신 남는 것' 같은 말은 쓰지 않는다
- 이 표의 '미포함'은 다른 차수 기능을 쓰지 않는 규칙의 예외. 미포함 가설의 해결책은 이 표에만 두고 구현 상세에는 쓰지 않는다

## KR 현재값과 실험 지표

- 현재값은 조회해서 채운다. '확인 필요'는 조회할 수 없을 때만
- 실험이면 지표마다 대조군에서도 잴 수 있는지 확인한다. 잴 수 없으면 판정 지표로 쓰지 않는다
- 개입하면 자동으로 바뀌는 지표(예: 기능을 켜면 무조건 생기는 클릭)는 판정 지표로 쓰지 않는다
- 관찰 기간이 필요한 지표는 실험 기간 안에 잴 수 있는 범위를 측정 칸에 쓴다 (예: '배정 뒤 14일, 실험 마지막 14일 배정분은 제외')
- 표를 채운 뒤 행 중복, 빠진 행, 판정 룰에 적힌 지표 개수가 KR 표와 같은지 확인
- 기능이 필요 없는 대상이 있는지, 그 대상이 기능을 끌 방법이 있는지 작성자에게 묻는다 (질문 단계에서 한 번)
