# 도메인 팩

스펙 초안을 쓰기 전에 대상 서비스의 사실 정보를 모아 `docs/spec-context.md`로 저장한다. 같은 프로젝트의 다음 스펙에서 재사용하고, 작성자가 요청할 때만 갱신한다. 이 파일에 없는 도메인 사실은 초안에 쓰지 않는다

## 양식 (docs/spec-context.md)

```markdown
# 도메인 팩: {서비스명}

갱신일: YYYY-MM-DD

## 서비스와 화면
| 화면 | URL 또는 경로 | 설명 | 출처 |
|---|---|---|---|

## 메뉴 구조
| depth1 | depth2 | 노출 조건 | 주요 기능 | 출처 |
|---|---|---|---|---|

## 관련 문서
| 문서 | 링크 | 무엇을 참고할지 |
|---|---|---|

## 용어와 코드 식별자
| 용어 | 뜻 | 코드 식별자 (출처) |
|---|---|---|

## API
| 용도 | 메서드와 경로 | 주요 필드 | 출처 |
|---|---|---|---|

## 이벤트
| 이벤트명 | 있음/없음 | 용도 | 출처 |
|---|---|---|---|
```

## 자동 조회 절차

도구가 있으면 순서대로 조회해 양식을 채우고, 없으면 그 항목은 작성자에게 묻는다

1. 레포: `README.md`, 라우트 파일(`app/`, `pages/`, `src/routes`)로 화면과 경로. 컴포넌트명은 파일명 그대로
2. Confluence: `searchConfluenceUsingCql`로 `title ~ "{서비스명}" AND type = page AND lastmodified >= now("-1y")`. 상위 5건의 제목과 링크를 관련 문서 후보로 제시하고 작성자가 고름
3. API 스펙: asp MCP(사내 API Stack Portal)가 있으면 화면명과 기능명으로 검색해 메서드, 경로, 주요 필드를 복사
4. 이벤트: Amplitude MCP `search_amp_data_taxonomy`로 이벤트명 존재 여부 확인. 있으면 "있음", 없으면 "없음(신규 제안)". 이벤트명을 만들어 내지 않음
5. 코드 식별자는 위 1, 3, 4에서 복사한 것만 적고 출처 열에 파일 경로나 도구명을 남김

## 수집 질문 (도구로 못 채운 항목만)

```
스펙을 쓰기 전에 다섯 가지만 확인합니다. 모르는 항목은 "모름"이라고 답해 주세요.

1. 어느 서비스의 어느 화면인가요? (URL이나 화면 이름)
2. 이 화면이 속한 메뉴 경로는요? (예: 마이페이지 > 이력서)
3. 참고할 기존 스펙이나 히스토리 문서 링크가 있나요? 아래 후보 중 고르셔도 됩니다.
   {Confluence 검색 후보 1~5}
4. 자주 쓰는 용어와 그에 대응하는 코드 이름(API, 이벤트, 컴포넌트)을 아시나요?
5. 관련 API가 있나요? (경로나 이름)
```

답을 받으면 양식에 채워 저장하고 "docs/spec-context.md에 저장했습니다. 다음 스펙부터 재사용합니다" 한 줄만 알린다
