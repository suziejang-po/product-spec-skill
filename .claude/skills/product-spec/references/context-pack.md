# 도메인 팩

스펙 초안을 쓰기 전에 대상 서비스의 사실 정보를 모아 `docs/spec-context.md`로 저장한다. 같은 프로젝트의 다음 스펙에서 재사용한다. 이 파일과 그 밖의 출처(첨부 자료, 대화, 기존 문서)에 없는 도메인 사실은 초안에 쓰지 않는다

- 서비스명은 작성자 요청에 나온 화면이나 기능 이름(예: "인재풀 제안 상세")과 레포 이름을 함께 쓴다. "원티드"처럼 넓은 이름 하나로 검색하지 않는다
- 채워진 항목이 하나도 없으면 저장하지 않는다. 빈 팩이 다음 실행의 출처가 되면 초안이 계속 비어 나온다
- 갱신일이 30일을 넘었거나 레포의 라우트 파일이 바뀌었으면 "도메인 팩이 {N}일 전 것입니다. 다시 모을까요?"라고 한 번 묻는다
- 저장 전에 `.gitignore`에 `docs/spec-context.md`가 있는지 확인하고, 없으면 "사내 API와 이벤트명이 들어가므로 공개 레포라면 gitignore에 넣으세요" 한 줄 안내

## 양식 (docs/spec-context.md)

```markdown
# 도메인 팩: {서비스명}

갱신일: YYYY-MM-DD

## 서비스와 화면
| 화면 | URL 또는 경로 | 설명 | 출처 |
|---|---|---|---|

## 메뉴 구조
| depth1 | depth2 | 노출 조건 | 주요 기능 (유저가 하러 오는 일) | 출처 |
|---|---|---|---|---|

## 관련 문서
| 문서 | 링크 | 무엇을 참고할지 |
|---|---|---|

## 용어와 코드 식별자
| 용어 | 뜻 | 코드 식별자 (출처) |
|---|---|---|

## API
| 용도 | 메서드와 경로 | 주요 항목 | 출처 |
|---|---|---|---|

## 이벤트
| 이벤트명 | 있음/없음 | 용도 | 출처 |
|---|---|---|---|

## Confluence 설정
| 항목 | 값 |
|---|---|
| spaceKey | WAN |
| 작성중 부모 페이지 | 4808376595 |
| 출시 확정 부모 페이지 | 4808212726 |
```

Confluence 설정은 기본값을 적어 두고, 팀이 다른 스페이스를 쓰면 작성자가 바꾼다

## 자동 조회 절차

도구가 있으면 순서대로 조회해 양식을 채운다. 도구가 없으면 화면, 메뉴, 참고 문서, 용어만 작성자에게 묻고 API와 이벤트는 빈칸으로 둔다

1. 레포: `README.md`, 라우트 파일(`app/`, `pages/`, `src/routes`)로 화면과 경로. 컴포넌트명은 파일명 그대로
2. Confluence: 첨부 자료와 대화에 적힌 페이지 ID나 링크를 먼저 전부 뽑아 관련 문서에 넣는다. 그다음 `searchConfluenceUsingCql`로 `title ~ "{화면 또는 기능 이름}" AND type = page AND lastmodified >= now("-1y")`와 `text ~ "{화면 또는 기능 이름}"`을 각각 조회해 상위 5건을 후보로 제시하고 작성자가 고른다
3. API 스펙: asp MCP(사내 API Stack Portal)가 있으면 화면명과 기능명으로 검색해 메서드, 경로, 주요 항목를 복사
4. 이벤트: Amplitude MCP `search_amp_data_taxonomy`로 이벤트명 존재 여부 확인. 있으면 "있음", 없으면 "없음(신규 제안)". 이벤트명을 만들어 내지 않음. 이벤트 description에 적힌 메뉴 경로는 메뉴 구조의 출처로 써도 되며 출처 열에 "Amplitude {이벤트명} description"이라고 적는다
   - 출처 문서에는 있는데 Amplitude에서 못 찾은 이벤트는 "미확인(문서명)"으로 적고 초안에서는 `⚠️ 이벤트 존재 확인 필요 → 데이터 분석가`
5. 코드 식별자는 위 1, 3, 4에서 복사한 것만 적고 출처 열에 파일 경로나 도구명을 남김

## 수집 질문 (도구로 못 채운 항목만)

작성자와 AI가 같은 그림을 보기 위한 질문. 작성자가 코드나 API를 모를 수 있으므로 화면, 메뉴, 용어처럼 작성자가 아는 것만 묻는다. API와 이벤트명은 도구(asp, Amplitude)로만 채우고, 도구가 없으면 묻지 않고 빈칸으로 둔다

```
스펙을 쓰기 전에 다섯 가지만 확인합니다. 아는 것만 답해 주시고, 모르는 항목은 "모름"이라고 해 주세요.

1. 어느 서비스의 어느 화면인가요? (URL이나 화면 이름)
2. 그 화면은 어느 메뉴 아래에 있나요? (예: 마이페이지 > 이력서)
3. 그 메뉴는 유저가 무엇을 하러 오는 곳인가요? 한 줄이면 됩니다
4. 참고할 기존 스펙이나 히스토리 문서 링크가 있나요? 아래 후보 중 고르셔도 됩니다
   {Confluence 검색 후보 1~5}
5. 이 스펙에서 자주 쓸 용어가 있나요? 팀에서 부르는 이름 그대로 알려 주세요 (예: "제안 상세 모달", "인재풀 제안")
```

답을 받으면 양식에 채워 저장하고 "docs/spec-context.md에 저장했습니다. 다음 스펙부터 재사용합니다" 한 줄만 알린다. 3번 답은 메뉴 구조 표의 주요 기능 열에, 5번 답은 용어 표에 들어간다
