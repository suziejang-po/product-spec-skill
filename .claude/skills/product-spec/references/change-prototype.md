# 변경 표시 프로토타입

지금 서비스 화면을 팀 디자인 시스템 또는 기본 컴포넌트로 재현하고, 이번 스펙에서 바뀌는 곳을 화면 안에 점선 상자로 표시한 HTML. 화면은 실제처럼 이어지고, 범례에서 변경 표시를 끄면 완성 화면처럼 보인다

- 대상: 디자이너, 개발자, 외부 협력사와 '지금 화면에서 무엇이 바뀌는지'를 같은 화면을 보며 맞추는 용도
- 화면 프로토타입(SKILL.md 「아티팩트 생성」)과 다른 점
  - 화면 프로토타입: 설명 패널에 요구사항 행을 그대로 띄움
  - 변경 표시 프로토타입: 바뀌는 요소 옆에 변경 내용과 출처를 상자로 붙이고, 상태로 색을 나눔

## 만드는 조건

- Phase 4 아티팩트 질문에서 작성자가 3번을 고른 경우
- 작성자가 스펙 작성 뒤 "변경 표시 프로토타입 만들어줘", "바뀌는 곳 표시한 화면 만들어줘"라고 한 경우
- 스펙이 없으면 만들지 않는다. "스펙을 먼저 만들어야 합니다" 한 줄 안내

## 먼저 읽을 것

1. `references/change-prototype-template.html`: 양식, 클래스, 동작 속성. 이 파일을 복사해서 시작
2. 대상 스펙 `docs/specs/{슬러그}/spec.md`의 화면 표 또는 구현 상세, 상태 표, 버튼/액션 표, `sources.md`
3. 현재 화면 캡처가 있으면 그 레이아웃을 따름. 없으면 상단 메뉴와 페이지 틀만 양식대로 두고 화면 내용은 스펙 행으로 구성
4. 팀 디자인 시스템 MCP가 연결돼 있으면 양식의 색 값과 컴포넌트 이름을 그 토큰, 컴포넌트와 대조. 다르면 디자인 시스템 값을 따름. 없으면 양식 기본값

## 시작 전에 작성자에게 묻는 것 (한 번에)

- 외부 요청 라벨: 외부에서 요청한 변경이 있으면 누구 요청인지 (예: 운영팀, 협력사 이름). 없으면 외부 요청 색을 범례에서 지움
- 디자인 기준본: 'NEW' 표시를 쓸 기준 시안의 이름과 날짜. 없으면 NEW 표시를 쓰지 않음

## 화면 구성

- 화면 하나가 `<section class="screen" id="{영문 슬러그}" data-name="{스펙 화면 ID}. {화면 이름}">` 하나
- 화면 순서는 스펙 화면 표 순서. 첫 화면은 사용자가 처음 들어오는 화면(진입점)
- 상단 메뉴는 이번 스펙의 진입점이 있는 메뉴만 `on`
- 기존 화면이면 바뀌지 않는 영역도 화면처럼 보일 만큼 그림. 바뀌지 않는 영역에는 표시를 달지 않음
- 화면 열이 `해당 없음 ({종류})`인 행(배치, 발송)은 화면으로 그리지 않음. 그 결과가 화면에 보이는 곳에 확인 필요 상자로 짧게
- 스펙에 없는 탭, 필터, 버튼, 배너를 더하지 않는다 (SKILL.md 「하지 않는 것」과 같음)
- 문구: 스펙에 확정 문구가 있으면 그대로, 없으면 요소 이름 + `(문구 워싱 필요)`
- 이미지: 넣지 않음. `.thumb`에 '썸네일'처럼 자리 이름만

## 변경 표시 규칙

- 상자는 바뀌는 요소 바로 아래. 한 상자에 변경 하나
- 상자 문구는 스펙 요구사항에서 가져와 한 줄로 줄임. 끝에 (출처 날짜)
  - 출처는 `sources.md`의 출처 이름. 출처가 구술이면 (PO {날짜})
- 색은 상태로 고름

| 표시 | 언제 |
|---|---|
| `.anno.confirmed` [확정] | 스펙에서 정해진 변경 |
| `.anno.request` [외부 요청] | 외부 요청으로 들어온 변경. 라벨은 작성자가 답한 이름 |
| `.anno.pending` [확인 필요] | 스펙에 `(… 확인 필요)`, `⚠️ 착수 조건`이 붙은 항목 |

- 요소 자체가 새로 생기거나 바뀌면 `data-mark`로 같은 색 테두리도 붙임
- 디자인 기준본 이후 바뀐 곳에만 `.tag-new.inline`
- 결정 과정, 번복 이력은 쓰지 않음. 최종 내용만

## 동작

양식의 `data-` 속성만 쓴다. 새 스크립트를 짜지 않음

- 화면 이동: `data-go`. 스펙 진입점 열과 맞춰 연결. 닫기, 이전 버튼도 연결
- 동의, 필수 체크 뒤 버튼 활성: `data-agree-group`, `data-agree-cta`
- 필수 입력: 스펙에 필수라고 적힌 항목만 `data-validate`
- 확인 창 `data-open`, `data-close`, 완료 알림 `data-toast`
- 상태별 화면(정원 참, 로그인 여부)은 화면을 따로 만들고 화면 이동 패널에서 고르게 함
- 서버 처리, 저장, 실제 본인확인, 결제는 흉내 내지 않음. 누르면 다음 화면으로만
- 주소 바꾸기(`history`), `localStorage`는 아티팩트와 미리보기 창에서 막힘. 양식처럼 `try` 안에서만 부르고, 실패해도 화면 전환이 되게 함

## 저장과 전달

- 저장: `docs/specs/{슬러그}/change-prototype.html`
- 스펙 1-7 참고(또는 비주얼 표)에 경로를 한 줄로
- 아티팩트를 올릴 수 있는 환경이면 같은 파일을 아티팩트로 올리고, 채팅에는 한 줄만
- 파일에 사내 API 경로, 이벤트명, 테이블명을 넣지 않음
- 실제 서비스 화면을 재현하므로 공개 범위를 확인하라고 한 줄 안내
- 파일 시스템이 없으면 HTML 전체를 출력

## 확인 (저장 뒤)

- 스펙 화면 행마다 화면이 하나씩 있고 화면 이동 패널에 모두 뜨는가
- 모든 `data-go`, `data-open`, `data-validate`, `data-toast`, `data-tab` 값이 실제 id를 가리키는가
- 변경 표시를 끄면 상자와 테두리가 모두 숨는가
- 스펙의 확인 필요 항목이 모두 [확인 필요] 상자로 있는가
- 스펙에 없는 요소가 화면에 없는가
- 375px 폭에서 가로로 넘치지 않는가

## 스펙이 바뀌면

- 스펙을 먼저 고치고, 바뀐 화면만 다시 씀. 상자 문구와 상태 색도 같이 고침
- 바로 반영하지 못하면 범례 옆에 `⚠️ 스펙 {날짜} 기준, 최신 아님`
